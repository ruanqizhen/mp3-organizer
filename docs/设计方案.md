# MP3 整理工具实现方案（调研结论）

> 目标：Windows 上的老 MP3 批量整理工具 —— 按类型/演唱者归类文件夹、元数据编码修复为 Unicode、完整性检查与修复、自动找专辑封面并嵌入。
> 调研日期：2026-10-19

## 1. 总体结论：可行，推荐 Python 技术栈

核心库全部有成熟现成方案，不需要从零造轮子：

| 功能 | 推荐方案 | 说明 |
|---|---|---|
| 标签读写 / 编码修复 / 封面嵌入 | **mutagen**（Python，1.48.x，GPLv2） | 无第三方依赖，Windows 兼容好，支持全部 ID3v2 版本；自带 `mid3iconv` 编码转换工具 |
| 完整性检测 + 部分自动修复 | **mp3val**（命令行 exe，SourceForge 可下） | 检测 MPEG 帧错误（sync 错、缺帧），`-f` 参数可修复一部分；2009 后未更新但 Win 下仍可运行 |
| 深度损坏检测（最终裁决） | **ffmpeg**（持续更新） | `ffmpeg -v error -i 文件 -f null -` 全程解码，报错即定位到秒级 |
| 封面来源（首选） | **MusicBrainz + Cover Art Archive** | `coverartarchive.org/release/{mbid}/front`，免费，需遵守 1 次/秒限流 + 自定义 User-Agent |
| 封面来源（备选） | **iTunes Search API** | 免费免 key，老中文歌覆盖率常更高，`artworkUrl100` 可换 600x600 |
| 打包成 Windows 软件 | **PyInstaller** | 打成单文件 exe；mp3val.exe / ffmpeg.exe 放同目录随包分发 |

Python 库用 `musicbrainzngs` 调 MusicBrainz API。数据量大时可考虑 `mutagen-rs`（Rust 加速版，Windows 有预编译 wheel）。

## 2. 功能一：按类型 / 演唱者自动归类

- 读 ID3 帧：`TCON`（类型）、`TPE1`（演唱者）、`TALB`（专辑）、`TIT2`（曲名）。
- 目标结构示例：`音乐库/<类型>/<演唱者>/<演唱者 - 专辑>/<曲名>.mp3`，模板可让用户自定义。
- 老文件坑点：
  - `TCON` 可能是 ID3v1 数字编号（如 `(13)` = Pop），mutagen 能转文字；
  - 类型/演唱者缺失 → 归入 `未知类型` / `未知演唱者`，最后在报告里列出人工补；
  - 目标文件重名 → 自动加序号，不覆盖。
- 顺序建议：**先做编码修复（功能二）再归类**，否则文件夹名会是乱码。

## 3. 功能二：元数据编码修复 → Unicode（核心难点，已有成熟解法）

老 Windows 中文 MP3 的典型病：ID3v2.3 标签帧声明编码为 latin1（或干脆没声明），实际字节是 **GBK/Big5**，读出来就是乱码。ID3v1 则根本没有编码概念，中文 Windows 当年直接写 GBK。

修复算法（逐文件、逐帧）：

```python
from mutagen.id3 import ID3

CANDIDATES = ["gbk", "big5", "shift_jis", "euc-kr", "utf-8"]

def fix_frame(text: str) -> str:
    raw = text.encode("latin1", errors="strict")  # 取回原始字节
    for enc in CANDIDATES:
        try:
            return raw.decode(enc)  # 第一个能完整解码的就是它
        except UnicodeDecodeError:
            continue
    return text  # 都不行，原样保留，标记人工看
```

- mutagen 自带的 `mid3iconv -e GBK 文件.mp3` 就是干这个的，批量场景建议自研（要记录"转换前后对照表"，支持回滚）。
- 写回时统一为 **ID3v2.4 + UTF-8**，兼容性最好（Windows 资源管理器、Foobar、手机播放器都认）。
- 批量前建议抽查：修完随机抽 20 首人工看一眼，防止把本来就是对的 latin1 文本误转。
- 文件名乱码是另一个独立问题（NTFS 本身是 Unicode，当年在 Windows 下存的文件名一般没问题；只有从 Linux/FTP 拷回来的才需要修），可作为可选项。

## 4. 功能三：完整性检查、修复、标记

三级流水线，按顺序做：

1. **mutagen 加载**：连标签头都解析失败 → 直接标"严重损坏"。
2. **mp3val 扫描**：`mp3val.exe 文件.mp3 -f -nb`（`-f` 自动修复，`-nb` 不备份由工具自己备份）。能修：坏帧头、Xing 头重建、填充错误；修完复检。
3. **ffmpeg 终检**：`ffmpeg -v error -i 文件.mp3 -f null -`，输出任何 error/warning 即按时间点记录；解码失败 = 修不好。

处理策略：

- 正常 → 绿灯；
- mp3val 修好且复检通过 → 黄灯"已修复"（原文件进 `_备份/`）；
- 修不好 → 文件名加 `[损坏]` 后缀 + 移入 `_待处理/` 文件夹 + HTML 报告列出错误原因（如"第 83 秒处帧损坏"），人工决定删还是留。

注意：mp3val 很老，中文文件名在它自带的前端下会挂，**只用命令行版并传完整路径**可避开；ffmpeg 做最终裁决更可靠。

## 5. 功能四：自动找专辑封面并嵌入

流程：用修复后的 `演唱者 + 曲名 + 专辑` 调 MusicBrainz 搜索 release → 取第一个高分结果的 MBID → 请求 Cover Art Archive：

```
GET https://coverartarchive.org/release/{mbid}/front-500
→ 302 跳转到 Internet Archive 的真实图片地址
```

- 准确率控制是关键：给每个匹配打分（标题/歌手/专辑相似度），低分进"待确认"清单，人工点选后再嵌入；**不要无脑全自动**，否则张学友的歌可能贴上张信哲的封面。
- 下载的图片本地缓存一份，避免重复请求；MusicBrainz 限流 1 次/秒，几千首歌要跑几小时，建议做进度条 + 断点续跑。
- 嵌入用 mutagen 的 APIC 帧（`image/jpeg`，500px 左右，单张几十到几百 KB，不会明显撑大文件）；同时可选项存一份 `folder.jpg` 在专辑目录。
- 中文老歌在 MusicBrainz 覆盖不全时，切 iTunes Search API 补：`https://itunes.apple.com/search?term=歌手+歌名&entity=album&limit=5`，免费免 key。

## 6. 落地形态（Windows）

- **MVP 先做命令行版**：`mp3tool.exe 扫描 D:\Music`，跑完输出一份 HTML 报告（每首歌：原路径 → 新路径、编码修复对照、完整性状态、封面状态）。
- **第二步再做 GUI**：tkinter（零依赖）或 PySide6（好看），表格列出每首歌状态，勾选后执行。
- **打包**：`PyInstaller --onefile`，mutagen / musicbrainzngs / requests 打包无坑；mp3val.exe、ffmpeg.exe 放 exe 同目录随包分发（ffmpeg 记得附 LGPL 说明）。
- **安全红线**：任何改写前自动备份原文件到 `_备份/`，全程写操作日志，支持一键回滚。批量工具没有回滚就是灾难。

## 7. 现有工具对照：要不要自己写？

| 工具 | 能做什么 | 做不了什么 |
|---|---|---|
| MusicBrainz Picard（免费） | 自动识别歌曲、补标签、下载封面、按模板整理文件夹 | 不管 GBK 乱码修复，不管损坏检测修复 |
| Mp3tag（Windows 免费） | 批量标签编辑、正则重命名、封面嵌入，正则很强 | 无自动编码修复，无完整性检测 |

结论：四个需求里"编码修复 + 损坏修复"正是现成工具的盲区，这就是自研的价值。封面和整理可以先用 Picard/Mp3tag 顶上，验证需求后再决定投入。

## 8. 建议的 MVP 开发顺序

1. 扫描 + 编码修复（见效最快，解决最痛的乱码问题）
2. 按类型/演唱者归类移动
3. 完整性检测 / 修复 / 标记
4. 封面匹配（最耗时的是调准确率，放最后）

每一步都先备份、可回滚。估计 MVP（命令行版）代码量约 800–1200 行 Python。
